# 项目中文注释与业务文档化设计

## 概述

为 Paperclip 项目核心业务模块系统性地添加中文注释，并在梳理过程中产出业务说明文档。目标是让后续开发人员能快速理解代码设计意图和业务流程。

## 注释规范

### 注释原则

- 代码体现"做什么"，注释体现"为什么"
- 只注释非显而易见的业务逻辑、设计意图、隐性约束

### 类/模块级注释

1-2 句说明模块职责、边界条件、设计约束。

### 函数/方法级注释

只注释以下情况：
- 非显而易见的业务规则（如"仅 local_trusted 模式下生效"）
- 隐性约束或假设（如"调用方已持有事务锁"）
- 边界条件处理（如"空数组表示不限制"）
- 设计权衡或临时方案（如"暂时用轮询替代 WebSocket"）

### 不注释的场景

- 标准 CRUD 操作
- getter/setter
- React 渲染模板
- 重复的类型定义
- 从命名能直接理解意图的代码

## 文档格式

每个模块产出 `docs/modules/<module-name>.md`，包含：

1. **模块概述** — 一句话说明模块目的
2. **核心流程** — 主要业务路径描述
3. **关键文件** — 文件清单及各自职责
4. **数据模型** — 涉及的核心表/类型
5. **上下游依赖** — 调用与被调用关系

## 执行顺序

1. shared — 基础类型和校验器
2. db — 数据库 schema 和迁移
3. Auth — 认证授权
4. Companies — 多租户
5. Agents — Agent 管理
6. Issues — 问题追踪
7. Goals — 目标管理
8. Projects — 项目管理
9. Routines — 定时任务
10. Approvals — 审批流程
11. Secrets — 密钥管理
12. Environments — 执行环境
13. Plugins — 插件系统
14. Dashboard — 仪表盘
15. Instance Settings — 实例配置

## 方案

采用方案 B：边注释边写文档。每个模块处理流程：

1. 通读模块所有源文件，理解整体结构
2. 给关键函数/类/接口添加中文注释
3. 产出该模块的 `docs/modules/<module-name>.md` 业务说明文档
4. 完成后 commit，标记进度
